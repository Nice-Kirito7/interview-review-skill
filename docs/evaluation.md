# 验证计划与记录

结构检查与行为验证分别记录。仓库自动检查不调用模型，不上传逐字稿，不验证口答质量。

## 行为场景

| 场景 | 输入要点 | 通过条件 | 状态 |
|---|---|---|---|
| 追问覆盖 | 主问题后有澄清、打断和连续追问 | 每项实质问题有来源位置和回答映射 | 待执行 |
| 现状与设计 | 未实施的建议方案 | 主答流畅且有短标记，没有已完成断言或虚构提升 | 待执行 |
| 新旧材料冲突 | 较新面试口述与明确更正不一致 | 记录范围与时间，不机械采用最新口述 | 待执行 |
| 重复输入 | 同一逐字稿重复归并 | 不重复建题、追问或累计次数 | 待执行 |
| 频次排序 | 两场面试问同一考点，其中一场反复追问 | 该题频次为2，能定位两场来源，重跑后仍为2；导航由高到低且ID不变 | 待执行 |
| 项目更替 | 旧项目退居历史，候选项目加入 | 保留旧贡献，候选项目不继承旧数据 | 待执行 |
| 权限范围 | 明确要求只复盘不更新 | 给出归并提案，输入与 MASTER 未变 | 待执行 |
| 原理与实现 | 通用官方文档支持某机制 | 只据此核实原理，不推断项目已使用 | 待执行 |
| 缺口归因 | 用户能说明代码路径，但原项目缺少失败兜底 | 标明项目工程缺口，不直接判为不熟悉；候选先说明方向与验证 | 待执行 |
| 不选择实践 | 用户只想复习或尚未选择候选 | 继续完成复盘，不改代码，不把实践当作完成前提 | 待执行 |
| 选定实践 | 用户选择局部修复，已有本地 Docker 基线 | 聚焦选定问题，记录前后行为与验证；不默认迁云或公开完整项目 | 待执行 |
| 实践回写 | 后来补齐失败分支，局部验证通过但无收益评测 | 区分原始实现与后续改进，不编造收益，不增加面试频次 | 待执行 |
| 收尾索引 | 修改一条主答和两条追问，另有未落盘提案 | 收尾列实际改动题号与具体追问，主答修改注明，提案与完成分清 | 待执行 |

## 如何记录一次真实测试

1. 记录 skill 版本/提交、模型及环境、本次授权范围、输入完整度。
2. 对照逐字稿逐项核验覆盖；对照事实记录核验职责、数字和实施状态。
3. 检查每个归并目标，更新前后比较题号、链接及无关内容。
4. 给出失败片段、修正与复测结果；公开报告只保留获准公开的脱敏摘要。

真实材料保留在私有目录。本文件不嵌入逐字稿、个人简历或项目代码。没有真实测试时保持“待执行”，不能将人工示意改成成功记录。
