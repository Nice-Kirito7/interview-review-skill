# 可选：由面试复盘延伸工程实践

用于复盘发现适合实践的项目缺口，或用户希望积累工程改进经历时。实践服务于能力积累；每次复盘可选择复习、回查实现或工程实践，不要求修改代码。

## 识别问题与提出候选

先判断薄弱点属于知识理解、表达组织、实现细节遗忘，还是原项目本身存在缺口。必要时回查实际入口和失败路径；证据不足时保留不确定性。工程兜底不完善不直接归因于用户不熟悉项目，方案合理也不代表已经实现。

对岗位相关、反复被追问、范围可控的问题，提出少量候选，分别说明要解决什么、如何验证、能积累什么能力。初次建议保持大方向，用户选择后再细化开发任务。用户已明确选择或授权的具体工作可直接推进，无需重复确认。

未选择工程实践时，用复习建议或候选清单结束本分支，继续交付复盘；没有改代码不影响复盘完成。

## 用户选择后进入开发

推荐本地开发、本地 Git 版本管理和 GitHub 远程备份，沿用已有项目约定和可运行基线。每次聚焦一个问题，记录原行为、修改理由、验证结果及剩余限制。已有 Docker 部署可以沿用，无需为展示迁移到云端开发。

开发任务围绕选定问题明确输入输出、改动边界和验收方式。验证应针对原问题，例如失败分支是否得到处理、重复请求是否产生重复副作用；需要对比效果时，保留可比基线、数据范围和条件。只通过局部测试时，只报告局部结论。

本分支可以接续用户授权的开发工作，但仅复盘或选择候选不自动授权发布私有代码、改变仓库可见性或部署生产服务。

## 私有实践与公开展示

完整项目依据授权范围优先私有管理。需要公开展示时，选择本人独立实现、具备公开权限的小模块，配合公开或合成数据、测试和简短说明。私有贡献的匿名统计可用于展示活跃程度，不能替代具体代码与改进成果。

## 验证后反馈 QA

完成选定实践并验证后，在已授权的 MASTER 维护范围内，将个人改动、选型依据、验证条件和效果增量定点同步到对应 QA；仅授权开发时先给回写提案。

保留原始实现、已认可设计、后来完成的改进和未验证效果各自的时间与证据。后来补齐的能力不能追溯成原面试时已实现；实现验证通过也不自动证明性能或业务收益。主答保持简洁，必要细节放追问和折叠备注。更新按现有 [MASTER 维护规则](maintenance.md) 执行。

后续实践改变答案不代表又发生一次面试，继续关联原题和实践记录，不增加面试频次。
